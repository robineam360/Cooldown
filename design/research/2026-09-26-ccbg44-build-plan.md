## Context

Android app, Kotlin, min SDK 31, target 36. Four home-screen widgets (Ring, Number, Countdown, All
accounts "Strip") drawn with `RemoteViews`. Unreleased: v1.8 is held for this bug; v1.7 has no
widgets. Code today (`app/src/main/java/com/robin/claudeusage/widgets/`):

- `WidgetFace.kt` — pure state (`FaceStates.of` → `FaceState` of `Cell`s), `Bucket` (9: Ring
  1×1/2×2, Number 2×1/4×1/4×2, Countdown 2×1/2×2, Strip 4×1/4×2), `Frame(bucket, wDp, hDp)` with
  `Frame.bucketFor` thresholds, geometry (`ring(frame)`, `bar(frame)`), `frameBytes` (the exact bitmap
  estimate, held equal to what `render` draws by a test), `render(context, face, frame, state)` →
  one single-size `RemoteViews`.
- `WidgetHost.kt` — `sizeMap`: one face per frame the launcher reports
  (`OPTION_APPWIDGET_SIZES`, smallest first, ≤ 4), drawn at exactly that frame and keyed 2 dp under
  it, in `RemoteViews(Map<SizeF, RemoteViews>)`; `withinBudget` drops the largest frames once the
  sum passes `BITMAP_BUDGET_BYTES` (2 MB today, always keeping the smallest); `wire` sets
  PendingIntents; `SafeUpdate` falls back to one single-size face if the update throws.
- Layouts `res/layout/widget_{ring,number,countdown,strip}{,_sd,_sl}.xml` are generated by
  `tools/widget_layouts.py` (three text-shadow variants each). `WidgetLayoutsTest` allows only
  RemoteViews-inflatable classes. Each face's update is wrapped in `widget_fresh` (`removeAllViews` +
  `addView`) so a state's views never survive into the next (CCBG-36 (Widget Reapply Residue)).
- `Transitions.kt` — R7: one inexact alarm at the next reset / stale edge of any placed widget.

## Plan — one piece, built by the session (rung 1), in this order

1. **Tiers on `Frame`** (pure): `tier` = S-narrow (H<140, W<240), S-wide (H<140, W≥240), T (H≥140,
   W/H<1.35), W (H≥140, W/H≥1.35); `roomy` = innerH ≥ 200. `bucketFor`, the nine buckets, `key()`
   and the size-map keying do **not** change, so R9's contract and the placed-widget prefs are
   untouched.
2. **Geometry** (pure, in `WidgetFace`): per Fable §3 — Ring Ø and figure per tier (cap 160),
   companion ring Ø100 when spare allows; Number figure sp by formula (32–72, 96 at innerH ≥ 300);
   Countdown count sp = clamp(min(innerW/4.5, innerH−118), 28, 80) on T/W, S formulas as given;
   Strip Ø = min((innerW−8(n−1))/n, innerH−62, 120) on T/W with cell pitch capped (Ø+40 / Ø+56);
   bar heights by tier. `frameBytes` adds the companion ring and uses the new caps, so the estimate
   stays exact.
3. **Layouts** (`widget_layouts.py`, regenerated): arrangements RemoteViews cannot switch at run
   time are **sibling groups toggled by visibility**, the pattern already used (`num_fig` /
   `num_fig_below`): Ring gets a vertical group (T) and a horizontal group (S-wide, W) plus a
   companion `ImageView` with bore text and a reset `TextView`; Number's control row is allowed in
   the 2×1 bucket for the T-narrow 2×2 (chips row + cycler row); Countdown gains an S-wide right
   column (figure + LEFT + bar) and a 32 sp figure row on T/W; the Chronometer gets
   `android:fontFeatureSettings="tnum"` as a static XML attribute; Strip's row becomes wrap_content
   and centred, each cell sized with `setViewLayoutWidth` (API 31 remotable). No `setOrientation` or
   other runtime layout-class change. Only the three variants' text style differs, as today.
4. **State**: `FaceStates.of` gives a Ring a `companion: Cell?` — the same account's other window,
   only when the account has both. Unassigned wording (Fable §3 "Unassigned (Q4)"): "(unassigned)"
   leaves every label; the stamp slot reads "tap to choose account"; Countdown 2×1 caption
   "5h reset · tap to choose"; Number 2×1 keeps its pill; the tap already opens config (CCBG-43
   (Widget Settings Hidden), f69af70).
5. **R7**: `Transitions` counts both windows' resets for a Ring whose account has both (the tier
   depends on the frame, which `Transitions` does not know; over-arming is safe under R4 — at most
   one extra inexact wake-up per 5 h).
6. **Wiring**: `WidgetHost.wire` wires chips and cycler by tier (Number 4×2 bucket, and the T-narrow
   2×1), not by bucket. The PendingIntent identity scheme (`cooldown-widget://<id>/<action>`) is
   unchanged.
7. **R10 budget 2 MB → 4 MB** (`WidgetFace.BITMAP_BUDGET_BYTES`), needed by the Strip's Ø120 × 4
   rings × two Fold frames (3.18 MB at 2.625 px/dp). `withinBudget`'s drop-largest rule and
   `SafeUpdate`'s fallback stay. Reasoning (Fable): the host's cap is 1.5 × screen px × 4 B
   (≈16 MB on 1080×2520, ≈6.9 MB on 720×1600); bitmaps over 16 KB cross Binder as ashmem blobs, so
   the 1 MB transaction limit is not the bound. The current 2 MB maps have updated fine on the Fold 7
   through Step 7 (the Strip 4×2 at two frames ≈1.2 MB) — not a test of 4 MB.
8. **Tests**: `WidgetFitTest` gains the six-column cover frames (84/156/244/333/510 × 108/237/366)
   and the inner 211×126 / 211×291 / 467×126 / 467×291, asserting no text run or bitmap exceeds its
   frame; formula tests per face; a budget test that every face's worst two-frame map is under 4 MB
   at densities 2.625 and 3.0; `revF_revDFramesKeepRevDGeometry` is replaced by a rev H invariance
   test; the gallery (`GalleryFixtures`) adds the tier frames. `./gradlew testDebugUnitTest` and
   `assembleDebug` green before each commit.
9. **Docs in the same commits**: ROADMAP R10 (budget), CCRM-79 (Ring Face) (reset line and
   companion), CCRM-80 (Number Face) (2×2 controls), rev F d.4 reversed; BUGS CCBG-44 status.
10. **Device check** (later, Robin present): release build on the Fold 7 over USB; place each face
    at the six-column sizes in Robin's shots, capture, and restore the phone (RUNBOOK Step 7's
    Before/After blocks). **Adopted from Astra:** the check proves the full size map was accepted,
    not `SafeUpdate`'s fallback — the app log shows no fallback line for any placed widget (and
    `SafeUpdate` logs one on every fallback, with the widget id); then, on the same placed widgets,
    fold and unfold (each screen draws its own frame's face) and resize each across a tier boundary
    (S→T→W) and back. Then v1.8 resumes at RUNBOOK Step 8.

## Reversal

All of it is unreleased app code and docs on `main`, in 2–4 commits: `git revert` of each, in
reverse order (so more than one command). No data, prefs key, provider name or on-device state
changes until the device check, which follows Step 7's restore blocks. Nothing is published until
RUNBOOK Step 8 (its own judge gate).

## What could go wrong (the ones I see)

1. The 4 MB map fails on a real host (TransactionTooLarge, or One UI's own cap) → `SafeUpdate`
   falls back to a single-size face, which on a Fold draws the cover frame on the inner screen too.
2. Sibling groups double the view count per face; inflate cost and the `widget_fresh` re-add on
   every update.
3. `fontFeatureSettings` on a Chronometer is ignored by the host → digits jitter at 80 sp.
4. Companion data: an account whose other window is absent or unsupported must never draw an empty
   second ring.
5. Test coverage is Robolectric-free JVM unit tests with fake density; real text metrics differ from
   the estimate, so the device check is the only proof of fit.
