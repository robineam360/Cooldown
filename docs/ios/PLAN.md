# Cooldown for iPhone and iPad — plan (23 Oct 2026)
review: calls=1 (1 full + ≤ 1 delta) effort=high · Astra 23 Oct: concerns ×2, both adopted (see Review disposition)

## Goal
A native Swift + SwiftUI app at `ios/` that tracks the same Claude and ChatGPT windows as the Android app, built from
the same repo and the same spec, running first on Robin's iPad Pro M4 and on iPhone simulators. Outputs: the APK as
today, plus an IPA. This is CCRM-7 (iOS), split into CCRM-92 (Shared Spec), CCRM-93 (iOS Spike), CCRM-94 (iOS App)
and CCRM-95 (Dual Release).

## Decisions already made (Robin, 23 Oct 2026)
1. The Android-only rule is lifted for exactly one more folder, `ios/`, plus a platform-neutral `spec/` (CLAUDE.md §3).
   The Mac stays in its own repo. Same model as EAM360 Inspect Lite: no code shared between platforms; both read
   `spec/`.
2. Signing for now: Robin's free personal Apple ID. The IPA is a personal build for his iPad (profiles last 7 days,
   at most 3 free-team apps per device). Later, if wanted: the paid EAM360 Apple Developer account signs it for
   colleagues (CCRM-95 (Dual Release) phase B).
3. Universal app, one target: iPhone and iPad. Hardware check on the iPad Pro M4; iPhone on the simulator only.

## Layout
- Android stays at the repo root for now. Moving it to `android/` (the Inspect Lite shape) is step 6, run only after
  v1.9 closes and when no other worktree branch is open, because it rewrites every Gradle, CI, RELEASING and WORKTREE
  path at once.
- `spec/` — Markdown and JSON only: the API contract and behaviour spec (seeded from CooldownMac's `contract/`), the
  captured Claude and ChatGPT payloads (moved from Android's test resources), and test vectors for pace, reset and
  number formatting taken from the Android tests. A check script rejects code files in `spec/`.
- `ios/` — XcodeGen `project.yml` is the source of truth, the generated `.xcodeproj` is gitignored. A local Swift
  package `ios/Packages/CooldownCore` holds models, parsers, pace maths, the API client and the account store protocol,
  so its tests run on the Mac in seconds without a simulator. The app target holds the UI, Keychain, notifications and
  background refresh. A widget extension holds the widgets and the Control Center control.
- Core logic is ported from CooldownMac's `CCooldownCore` (Swift to Swift), each file noting its source, and is then
  owned here. No package dependency on the Mac repo.

## What the iPhone and iPad can show (answers "always-on notification?")
iOS has no persistent notification and no reliable background polling, so the Android pinned notification does not
port. The surfaces, each needing a wireframe approved under CLAUDE.md §2 before it is built:
- **The app** — accounts, the 5h and Weekly windows, pace, charts; two columns on iPad.
- **Home-screen widgets** (iPhone and iPad) — small, medium and large, the Ring and Bar designs from CCRM-78 (Widgets
  Reborn). Usage numbers refresh on WidgetKit's budget (roughly tens of refreshes a day, so minutes-to-hours stale);
  the reset countdown ticks live because it is a date, not a fetched value.
- **Lock-screen widgets** (iPhone and iPad) — circular ring and rectangular line: the closest thing to the status-bar
  ring.
- **Control Center control** — the counterpart of the Quick Settings tile; opens the app.
- **Reset alerts** — local notifications scheduled ahead from the known reset times, so they fire with no background
  work; the counterpart of the reset pings.
- **Live Activity** — iPhone lock screen and Dynamic Island for the current 5h window; at most 8 hours, updated only
  when the app or a background refresh runs. Built last, iPhone only (iPad support UNVERIFIED, checked in step 2).
- Not ported: always-on notification, threshold alerts that need polling, anything Claude-only and ToS-disabled
  (CCRM-17 (Window Pings) stays off).

## Steps
1. **Rule and tracker** (this commit). CLAUDE.md §3 lifted; CCRM-7 (iOS) points here; CCRM-92 to CCRM-95 filed.
   Reversal: one revert.
2. **CCRM-93 (iOS Spike)** — the free-team facts everything else rests on, proven on the iPad before any feature work:
   a bare app plus widget extension, generated by XcodeGen, signed by the personal team (team id passed on the command
   line, never committed), installed with devicectl. Pass means: App Groups and a shared Keychain group work for the
   app and the widget on a free team; a development IPA exports from an archive; the bundle id is accepted; Live
   Activity availability on iPadOS is recorded. Robin does the Xcode account sign-in, Developer Mode and the trust
   prompt. If App Groups are refused on a free team, the plan stops here and the widget question goes back to Robin
   (paid account earlier, or app-only on iOS). Reversal: delete `ios/` and the app from the iPad.
3. **CCRM-92 (Shared Spec)** — create `spec/`, move the two payload fixtures there, point Android's test resources at
   it, add the vectors and the no-code check. Gate: Android's verify command passes unchanged in result.
4. **Wireframes** for every surface above, all states (empty, signed out, error, at 100 %, above pace, iPhone and
   iPad widths), in `design/`. Robin approves before step 5.
5. **CCRM-94 (iOS App)** — CooldownCore first (tests on the spec vectors and payloads), then sign-in (Claude token
   paste and the ChatGPT device code, both as on Android), the app screens, widgets, lock-screen widgets, the control,
   reset alerts, Live Activity. CI gains a macOS job running the package tests and a simulator build. Each piece:
   tests green, then a check on every platform it supports — iPhone simulator and iPad simulator, plus the iPad device
   for surfaces that run on iPad. iPhone-only pieces (the Live Activity, the Dynamic Island) are accepted on the
   iPhone simulator alone, and their behaviour on a physical iPhone is recorded as UNVERIFIED until one is used.
6. **Android to `android/`** (optional, after v1.9) — one move commit, every path updated, its own Astra call since
   it is a separate plan.

## Outputs and releases — CCRM-95 (Dual Release)
- **Phase A (free team, now):** the IPA is a local build output next to the APK, installed on the iPad over USB; it is
  not attached to GitHub releases, because nobody else can install it.
- **Phase B (EAM360 paid account, later):** colleagues install on their own iPhones and iPads with their own Apple
  IDs, by TestFlight (a public link, up to 10,000 testers, builds pass Beta App Review and expire after 90 days) or ad
  hoc (each device's UDID registered, 100 per device type a year). App Review may read the Claude sign-in as use of
  another company's service (CCRM-8 (Mac Menu-Bar) recorded the risk); TestFlight's beta review is the test of that.
  The EAM360 team would be the publisher of a personal MIT app, which Robin settles with EAM360 first. Access is by
  an invitation to the EAM360 team (App Store Connect and the developer account, role App Manager or Developer) for
  Robin's own Apple ID, never a shared login or a copied signing certificate; the ad-hoc or TestFlight build is then
  signed with Robin's own team membership and the team id stays out of the repo.
- **Release rule (binding from the first GitHub release that carries an IPA, i.e. phase B; phase A's local IPA is
  exempt and never becomes a release asset):** one GitHub release carries both the APK and the IPA under one
  version. Never an iOS-only release: the Android update check (CCRM-87 (Update Channel)) reads `releases/latest` and
  would find no APK. RELEASING.md gains the iOS steps in phase B.

## Risks
Free-team limits (7-day re-sign, 3 apps) make the iPad build a test bed, not a daily driver. Widget staleness is
built into iOS and must be visible in the design, not hidden. Two native apps double feature work; the spec, its
vectors and one commit per feature across platforms keep them from drifting.
